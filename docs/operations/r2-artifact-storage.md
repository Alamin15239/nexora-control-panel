# Production R2 artifact storage

## Purpose

The API already implements a bounded, one-time upload capability and streams accepted build archives into the Worker binding named `ARTIFACTS`. This document defines the production bucket dependency. It does not enable publishing: uploaded artifacts remain private staging objects until the separate archive-validation and publisher milestones are complete.

## Production resource

- Bucket name: `nexora-deployment-artifacts`
- Worker binding: `ARTIFACTS`
- Object key prefix: `staging/{organizationId}/{projectId}/{deploymentId}/{random}.tar.gz`
- Maximum object size: 100 MiB
- Accepted content type: `application/gzip`
- Integrity: the upload endpoint requires a lowercase SHA-256 digest and supplies it to R2's checksum validation.
- Access: Worker binding only. Do not enable R2.dev public access, a custom domain, or public bucket access. Do not create S3 access keys for the application.

## Provisioning sequence

**Do not merge the binding change until the bucket exists.** The production API deployment workflow is triggered by changes to `apps/cloudflare-api/wrangler.toml`; merging first would attempt to deploy a binding to a bucket that may not exist.

From the repository root, after authenticating Wrangler to the intended Cloudflare account:

```bash
pnpm --filter @nexora/cloudflare-api exec wrangler r2 bucket create nexora-deployment-artifacts
pnpm --filter @nexora/cloudflare-api exec wrangler r2 bucket list
```

Verify that the bucket appears in the expected Cloudflare account. Do not use a preview or development bucket for production customer artifacts.

After provisioning, merge the reviewed binding change. The normal production API workflow will deploy the Worker with the R2 binding. Then verify the deployed Worker configuration and the API's fail-closed behavior before enabling any deployment workflow.

## Retention and operations

Before accepting customer uploads, configure and document an R2 lifecycle rule for the `staging/` prefix. The retention period must be aligned with the deployment/rollback policy; do not delete artifacts that are still needed for an active validation or rollback. Monitor bucket storage, upload failures, and abandoned staging objects. A cleanup task must only delete objects whose deployment is terminal and whose retention window has elapsed.

## Security invariants

1. The bucket is private and is never exposed through a public hostname.
2. Raw upload capabilities are single-use, short-lived, and stored only as hashes in D1.
3. Object keys are generated by the API; callers cannot choose a key.
4. Uploads are streamed with a required Content-Length and a hard 100 MiB cap.
5. R2 validates the supplied SHA-256 checksum against the uploaded bytes.
6. Organization, project, deployment, repository, commit, and checksum metadata are server-derived.
7. R2 storage does not authorize extraction or publication. No customer archive is extracted by the Worker, agent, or privileged daemon in this milestone.
8. The dashboard Deploy action remains disabled until the separate isolated publisher and rollback gates are complete.

## Verification checklist

- [ ] Bucket exists in the intended Cloudflare account.
- [ ] Public R2.dev URL is disabled.
- [ ] No custom domain is attached.
- [ ] Lifecycle policy for staging artifacts is configured and reviewed.
- [ ] Worker binding `ARTIFACTS` is present after deployment.
- [ ] API returns 503 from OIDC exchange when the binding is absent.
- [ ] A test upload with a matching digest succeeds in a disposable deployment.
- [ ] A test upload with an incorrect digest is rejected by R2.
- [ ] Oversized, truncated, repeated, expired, and cross-deployment uploads are rejected.
- [ ] No object can be fetched anonymously.
- [ ] Publishing remains disabled.
